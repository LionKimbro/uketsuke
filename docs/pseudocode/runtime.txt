The one-turn receptionist machine.

OWNS
  resolving one uketsuke turn
  identifying and performing the absolute highest-priority available
  receptionist action
  the priority order among pending receptionist actions
  dispatching an active job through the configured host
  sending a completed job's result
  retiring a job after its result has been sent
  globally inspectable facts about the most recent turn

READS
  the active job, when one exists
  the inbox, when there is no active job

CALLS
  the machine responsible for the selected receptionist action

MAY SAFELY ASSUME
  that startup initialization has completed
  that the configured directory tree exists

ENSURES
  that do_tick performs at most one meaningful receptionist action
  that a True-returning do_tick performs the absolute highest-priority
    action available at that time, when there is one
  that do_tick returns True while the host should call it again
  that do_tick returns False when runtime is done
  that the runtime state panel describes the most recent turn

DOES NOT OWN
  the host program's forever loop
  scheduling, sleeping, or process lifetime
  durable job-record transitions
  filesystem primitives
  the host's interpretation of an opaque request or the work it performs

g = {
    "operation": None,
    "quit": False,
}


panel = {
    "turn-count": 0,
    "last-operation": None,
    "last-result": None,
    "last-error": None,
    "quit": False,
}


def do_tick():
    return False immediately if the system is in the quit state

    panel["turn-count"] += 1
    clear_the_observation_facts_for_this_new_turn()

    g["operation"] = identify_what_needs_to_be_done()

    if g["operation"] is None:
        panel["last-operation"] = "idle"

    otherwise:
        perform g["operation"]
        set panel["last-operation"] to the descriptive name of g["operation"]

    return True if we continue, False if the system is now in the quit state


def clear_the_observation_facts_for_this_new_turn():
    panel["last-operation"] = None
    panel["last-result"] = None
    panel["last-error"] = None


def identify_what_needs_to_be_done():
    examine the active job and inbox according to the planned priority order

    if the active job has status "dead-letter-pending":
        return the operation that completes the dead-letter transition:
          use the failed summarize-request history timestamp to construct
              both named dead-letter destinations
          if the working opaque request file exists:
              copy it to its named dead-letter destination
          set the in-memory job status to
              "transferred-to-dead-letter-directory"
          TEMPORARY, PENDING HISTORY-MECHANISM DESIGN:
              manually append the dead-letter transfer history entry
          write the changed job record as JSON to its named dead-letter
              destination
          if the working opaque request file exists:
              delete it from working
          delete the working job record

    if there is an active job that needs work:
        TEMPORARY, FOR THE CURRENT IMPLEMENTATION CYCLE:
          return no operation; the runtime idles because it does not yet
          know how to perform the active job's work

    if there is a result that needs to be sent:
        return the operation that sends the result and moves the job to done

    if there is a task that needs to be done:
        return the operation that does the task and moves the job to the
        state from which its result will be sent

    if there is an inbox message available to claim:
        return perform_operation_claiming_an_inbox_request

    return None


def perform_operation_claiming_an_inbox_request():
    follow the planned claim procedure in CLAIMING.txt
    set the operation's readable identity to "claim-inbox-request"


def transition_to_the_quit_state():
    Set g["quit"] to True, set panel["quit"] to true.

PLANNED PRIORITY ORDER

These are part of the intended routine, but are not all implemented in
the current cycle.

  1. complete a dead-letter-pending transition
  2. send a result, then move the job to done
  3. do a task, then move the job to the state from which its result
     will be sent
  4. claim an inbox message and create its job
  5. otherwise, there is no work
