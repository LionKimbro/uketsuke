The future request-claiming transition.

This is a design note.  It does not currently render into a Python
module.


## Current decisions

The inbox is passive.  It does not need its own machine.  Runtime will
select a claim action when there is no active job, no higher-priority
work, and an inbox request is available.

Claiming brings an opaque inbox request into the working area as
`opaque-request-file` and creates the active job when the request can
be understood.

An orphan `opaque-request-file` without an active job is not dangerous.
The job record, rather than the contents of `working/`, is the primary
source of lifecycle truth.  Orphan cleanup is useful for neatness but
does not need aggressive recovery machinery.


## Claim and recovery direction

The active job record is the durable boundary of a completed claim.

Before `job.json` exists, the inbox file remains the source of truth.
If a crash leaves an orphan `opaque-request-file`, a later claimant may
ignore or replace it while the inbox source remains available.

The host summary is obtained after an opaque copy has been placed in
working, but before the initial claimed job is durably created. The
claiming process supplies `jobs.create_new(info)` with the returned
request-id and the request's original filename.

After a claimed job exists, startup treats the job as the source of
truth.  If an inbox file appears with the job's
`request-original-filename`, startup deletes that duplicate inbox file.

In the normal claim path, immediately after a new claimed or
dead-letter-pending job has been durably recorded, claiming deletes the
original inbox file that was copied into working.  Startup's duplicate
removal is the crash-recovery backstop for an interruption before that
ordinary deletion.

The selection rule for an inbox claim is: choose the file with the
highest `last-modified` value returned by `list-files`.


## Summary timing

The host `summarize-request` function supplies the request-id that
uketsuke needs for the job.

Summarization is part of claiming.  It occurs after the raw request has
been copied into working and before the initial job record is durably
created.


## Failed summary outcome

If the host cannot recognize or summarize the request, uketsuke must
preserve both the raw request bytes and a job record explaining the
failure in `dead-letter/`.

The failed summary immediately creates a `dead-letter-pending` job.
That job has `request-id: None`, the captured error, and the initial
history entry whose timestamp determines its later dead-letter
filenames.


## No `summarized` status

`claimed` means that the request was successfully summarized and is
ready for execution.  A summary failure does not become claimed.


## Planned claim procedure

```text
list the immediate inbox files with their last-modified times
select the file with the highest last-modified time

remember its filename as request-original-filename
copy it to working/opaque-request-file

ask the host to summarize working/opaque-request-file

if the summary succeeds:
    prepare successful-claim info
    jobs.create_new(info)

if the summary raises:
    capture its exception trace
    prepare failed-summary info
    jobs.create_new(info)

delete the selected original inbox file
```
